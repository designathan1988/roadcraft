# Test impact analysis, selective test execution, fast type checking and linting (state as of 2026-10-21)

Project context (read from the repo's package.json/tsconfig.json, 2026-10-21): vitest ^4.1.11, vite ^8.2.2, typescript ^5.9.3, @typescript/native-preview ^7.0.0-dev.20260707.2 (the `typecheck` script already runs `tsgo --noEmit -p tsconfig.json`), eslint ^10.9.0 with a suppressions baseline, `moduleResolution: "bundler"`, uses `paths` (no `baseUrl` found by grep). This matters: `experimental.recordDependencies` exists only in Vitest 5.0.4+, so the project would have to upgrade from 4.1 to use it.

## 1. Vitest `related`, `--changed`, `experimental.recordDependencies`; Jest equivalents

### Takeaway
By default Vitest and Jest pick tests from the **static import graph** (changed file → every test file that transitively imports it). Both docs say outright that dynamic imports with a computed path (`import(filepath)`) or dynamic requires are missed. Vitest 5.0.4 (12 Oct 2026) added an experimental `recordDependencies` mode. It uses the set of modules each test file **actually loaded** at runtime the last time it ran, instead of parsing the graph again. A file with no record always runs. This mode catches runtime-only edges and skips the transform phase, but it is new, experimental and needs Vitest 5.

### Cited Findings
- `vitest related /src/index.ts /src/hello-world.js` runs only tests that cover the listed source files. It follows static imports (and literal `import('./index.js')`) but not dynamic ones such as `import(filepath)`. It starts watch mode by default, so pass `--run` (e.g. in lint-staged). The docs page was at v5.0.5. — [Vitest CLI docs](https://vitest.dev/guide/cli)
- `--changed [since]` (default `false`) "Run tests that are affected by the changed files". `since` takes a commit or branch (docs give `origin/main` / `HEAD~1` as examples under `coverage.changed`). Change detection goes through `experimental.vcsProvider`, default `git`. — [Vitest CLI docs](https://vitest.dev/guide/cli)
- `experimental.recordDependencies` (CLI `--experimental.recordDependencies`, default `false`) records in the cache the modules each test file loads. `--changed` and `--related` then use those records "instead of the static module graph". "A test file without a record always runs." — [Vitest CLI docs](https://vitest.dev/guide/cli)
- PR #11515 (sheremet-va, opened 6 Oct 2026, merged 8 Oct 2026): `--changed`/`related` "statically parse the module graph". The new option "keeps a cache of files that ran previously to compare against". It is much faster when nothing needs to run because Vitest can "avoid transform phase entirely". Module IDs are added to the worker state's dependency set as the module runner imports them, reusing the hook already used for watch mode and mocking. A later commit added support for `viteModuleRunner: false` (native loader). Reviewers noted that a partial run can miss dynamic imports of skipped tests, so the PR was changed: "We no longer create a record if it's partial." The author plans to use vite-task to collect every file a process touches. A related PR #11516 adds `--since-last-run`. — [vitest PR #11515](https://github.com/vitest-dev/vitest/pull/11515)
- Release history: v5.0.4 (12 Oct 2026) "Add an option to cache dependencies instead of statically parsing them" (#11515), "Track project files and mocks with --changed" (#11432), "Print how many tests were affected and a total when running `--changed`" (#11424), "Enable fsModuleCache by default" (#11435). v5.0.5 (15 Oct) handles quoted file names in `--changed` (#11583). v5.1.0-beta.1 (19 Oct) "Rerun setup files after `--changed` filtering" (#11621) and "Reuse fsModuleCache in static collection" (#11622). v5.0.0 (3 Sep 2026) parses files statically in `vitest list` by default. — [Vitest releases](https://github.com/vitest-dev/vitest/releases)
- Jest `--findRelatedTests <files>` finds and runs "the tests that cover a space separated list of source files", and is meant for pre-commit hooks. `--onlyChanged/-o` "requires a static dependency graph (ie. no dynamic requires)" and only works in git/hg. Other flags: `--changedSince <branch|sha>`, `--lastCommit`, `--changedFilesWithAncestor`. `--watch` defaults to `-o` behaviour and `--watchAll` reruns everything. — [Jest CLI docs](https://jestjs.io/docs/cli)

### Inferences
- What the static graph misses in a three.js/Vite game. (1) Computed `import()` paths. (2) Web workers created with `new Worker(new URL('./x.worker.ts', import.meta.url))`. The worker module is not a static import of the test's module graph unless a test imports it directly. The docs do not say how Vitest treats this, so it is a likely blind spot. (3) Shared global or singleton state and test ordering. (4) Non-code inputs: JSON/data assets read via `fs`/`fetch`, shaders loaded as strings, `vite.config`/`vitest.config` and setup files. Jest's docs list none of these as covered, and Vitest only began tracking "project files and mocks" in 5.0.4. (5) Type-only changes, which can break type checking without changing any runtime module.
- recordDependencies covers (1) and partly (2), but only for code a test actually executed. Branches that did not run in the recorded run, and inputs read through `fs`, are still invisible. Edits that add a *new* dependency are caught only because the edited file is itself in the old record.
- Barrel/index files and widely imported core modules (e.g. `src/core/*`) make the static "related" set balloon. A change to a hub module can still select most of the ~650 specs. Selection saves the most on leaf changes.
- Real-world speedups for vitest `--changed`/`related` on large repos: no published measured numbers found (see Gaps). The saving depends on the change's fan-in in the graph.

### Gaps
- No independent benchmark of `vitest --changed` or `recordDependencies` speedups was found. PR #11515 claims "significantly faster" with no number in the part read (the page was truncated at 100k of 196k chars).
- On-disk location of the record cache is not documented in what was read. Explicit handling of Web Workers is not documented by Vitest.

## 2. How Nx, Turborepo, Bazel, Google TAP, Meta PTS, Launchable and Datadog TIA decide what to test

### Takeaway
Build/monorepo tools (Nx, Turborepo, Bazel/TAP) all use **graph reachability from changed files**. They work at project/package/target granularity, which is coarser than Vitest's file graph. ML systems (Meta PTS, Launchable) add **probabilistic ranking** on top of that and trade a small miss rate for running far fewer tests. Meta's paper reports 2x lower cost while still reporting >95% of individual test failures and >99.9% of faulty changes. Coverage-based TIA (Datadog) skips a test only if every file it covered is unchanged since a recorded passing run. All of them recommend a periodic full run as a safety net.

### Cited Findings
- **Nx affected:** uses Git to list changed files, maps them to projects through the project graph, then adds the projects that depend on them. By default every task of an affected project runs. `NX_LEGACY_AFFECTED=false` selects individual tasks by whether the change reaches the task's `inputs`, and `--explain` shows why. Base defaults to `main` and head to the working tree (`--base/--head`, `NX_BASE/NX_HEAD`). `--files` works without Git. Savings are small when many projects are affected. — [Nx affected docs](https://nx.dev/docs/features/ci-features/affected)
- **Turborepo `--affected`:** equivalent to `--filter=...[main...HEAD]`. Works per package by default, and `futureFlags.affectedUsingTaskInputs` narrows it to each task's `inputs` globs. In shallow clones every package is treated as changed. Base and head can be overridden with `TURBO_SCM_BASE/TURBO_SCM_HEAD`. — [Turborepo run reference](https://turborepo.dev/docs/reference/run)
- **Google TAP:** handles CI for "the vast majority" of Google's ~2 billion LOC monorepo. Findings: "very few of our tests ever fail", failing tests are generally "closer" to the code they test, frequently modified code and certain users/tools cause more breakages, and code recently modified by more than 3 developers breaks more often. Memon et al., ICSE-SEIP 2017, pp. 233–242. — [Memon et al. abstract](https://www.cs.umd.edu/~atif/pubs/Memon_2017_TGC_3103112.3103143-abstract.html)
- **Meta Predictive Test Selection (Machalica et al., ICSE-SEIP 2019):** in production it cuts the total infrastructure cost of testing code changes by 2x while guaranteeing that over 95% of individual test failures and over 99.9% of faulty changes are still reported. It models test flakiness. — [arXiv 1810.05286](https://export.arxiv.org/abs/1810.05286); [ICSE 2019 page](https://2019.icse-conferences.org/details/icse-2019-Software-Engineering-in-Practice/22/Predictive-Test-Selection)
- Meta engineering blog: PTS catches more than 99.9% of regressions before they reach trunk while running about one third of the tests that transitively depend on the modified code. Graph-based selection is the baseline and ML prunes it further. — [Meta engineering blog](https://engineering.fb.com/developer-tools/predictive-test-selection/)
- **Launchable (now CloudBees Smart Tests):** `--confidence 90%` asks for a subset "expected to find 9 out of 10 failing runs". The confidence curve comes from held-out sessions. A changelog example finds 90% of failing runs in 40% of the time. Marketing says failures are found "up to 80% faster" and recommends periodic full runs. — [Launchable docs](https://help.launchableinc.com/features/predictive-test-selection/requesting-and-running-a-subset-of-tests/choosing-a-subset-optimization-target/how-a-confidence-curve-is-generated/); [Launchable product page](https://launchableinc.com/predictive-test-selection)
- **Datadog Test Impact Analysis:** maps each test (or suite, depending on framework) to the repository files it covers, collecting coverage automatically. A test is skipped if it previously passed on a commit where its covered and tracked files were identical. By default it cannot detect changes to library dependencies, compiler options, external services, or data files in data-driven tests. For that reason the default branch is excluded from TIA. Coverage collection itself adds overhead. — [Datadog TIA docs](https://docs.datadoghq.com/tests/test_impact_analysis/)

### Inferences
- For a single-package repo like this one, Nx and Turborepo add nothing at test granularity because everything is one package. Their value is task caching. Vitest's own file graph is the right level.
- Datadog's coverage-skip approach is conceptually close to Vitest's `recordDependencies`: both use recorded runtime dependencies and skip a test when none of them changed. Both have the same blind spots (data files, config, external state).
- Meta's numbers support a per-change subset plus a periodic full run. A ~1% miss per change is acceptable only when a full suite runs before commit or merge.

### Gaps
- The TAP PDF body could not be extracted (compressed streams), so its quantitative selection numbers are missing. Bazel docs were not fetched in the budget. Bazel's model (rebuild and retest targets whose transitive inputs changed, with cached test results) is general knowledge here and not sourced in this note.
- No measured engineering-blog numbers from Shopify, Airbnb, Slack, Uber, Figma or Vercel on JS test selection were found within the search budget.

## 3. Fast type checking: TypeScript 7 native, incremental, isolatedDeclarations

### Takeaway
TypeScript 7.0, the Go native port, went **stable on 8 Jul 2026**. It ships as the normal `typescript` package with a `tsc` binary, and `@typescript/native-preview`/`tsgo` was the preview channel. Official full-build speedups are 7.7–11.9x with the default 4 checkers. Independent tests on type-heavy code show 3.9–7.3x. It hard-errors on `baseUrl`, `moduleResolution: node10/classic`, `target: es5` and similar, and 7.0 has no stable programmatic API (expected in 7.1). This project already runs `tsgo` from a pre-release native-preview build (dev.20260707) and keeps `typescript ^5.9.3` for tools.

### Cited Findings
- Release 8 Jul 2026. `npm install -D typescript` provides `tsc`. Nightlies move from `@typescript/native-preview` to `typescript@next`. `@typescript/typescript6` provides `tsc6` so it can run side by side, and npm aliases are recommended so typescript-eslint can still import `typescript`. — [TypeScript 7.0 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7.0/)
- Benchmarks TS6 → TS7 (default `--checkers 4`): vscode 125.7s→10.6s (11.9x), sentry 139.8→15.7s (8.9x), bluesky 24.3→2.8s (8.7x), playwright 12.8→1.47s (8.7x), tldraw 11.2→1.46s (7.7x). With `--checkers 8`: vscode 7.51s (16.7x), tldraw 1.06s (10.6x). Memory falls 6–26%. In the editor, opening a file with an error in VS Code went from ~17.5s to <1.3s. — [TypeScript 7.0 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7.0/)
- Flags: `--checkers N` (default 4; more uses more memory, and rare order-dependent results are possible), `--builders N` for parallel project-reference builds under `--build` (multiplies with checkers), `--singleThreaded`. `isolatedDeclarations` is noted as a way around the project-graph bottleneck under `--build`. — [TypeScript 7.0 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7.0/)
- Hard errors in 7.0: `target: es5`, `downlevelIteration`, `moduleResolution: node/node10/classic`, `module: amd/umd/systemjs/none`, `baseUrl` (make `paths` relative to the project root instead), `esModuleInterop:false`, `alwaysStrict:false`, import `asserts`. New defaults: `strict: true`, `module: esnext`, `types: []` (restore with `["*"]`), `noUncheckedSideEffectImports: true`. No stable API in 7.0, so typescript-eslint type-aware rules and the Vue/Svelte/Astro/Angular tooling stay on 6.0. — [TypeScript 7.0 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7.0/); [InfoQ](https://infoq.com/news/2026/08/typescript-7-released/)
- Independent M4 Mac mini test: lobe-chat 7.3x, Effect 5.3x, drizzle-orm 3.9x. `--checkers 8` was *slower* on a 16 GB machine because of memory pressure. — [lilting.ch benchmark](https://lilting.ch/en/articles/typescript-7-native-benchmark)
- Practitioner advice: benchmark clean, warm, incremental and `--noEmit` runs separately, because otherwise "you're measuring your cache". `.tsbuildinfo` placement and CI cache keys are common migration pain points. — [kunalganglani.com](https://www.kunalganglani.com/blog/typescript-7-native-compiler-benchmark)

### Inferences
- `types: []` as the new default may break ambient types (e.g. `vite/client`, `vitest/globals`, `@webgpu/types`) unless `types` is set explicitly. Check this when moving from the July preview to 7.0.x stable.
- For a ~200k LOC single project, the ~12 s tsc figure is likely the TS5 `tsc` path. With tsgo at 4 checkers, a 7–10x speedup would put it at roughly 1.2–2 s, which is an estimate from the published ratios, not a measurement. `--incremental` with a persisted `.tsbuildinfo` should cut no-op and leaf-change runs further. Type checking cannot be scoped to "affected files" the way tests can, because a type change ripples through. A whole-program `tsgo --noEmit` is the cheap, safe choice.
- `isolatedDeclarations` only helps with project references or `--build` graphs. For one tsconfig it adds annotation burden for little gain.

### Gaps
- The TS 7.0 announcement read here does not detail `--incremental` behaviour or tsbuildinfo compatibility in the native compiler. Plugin (language service plugin) support was not covered beyond "no stable API".

## 4. Fast linting: oxlint (+ tsgolint), Biome, ESLint cache / changed files

### Takeaway
oxlint type-aware linting (tsgolint v7, built on TS 7) is **stable as of 22 Jul 2026**. It covers 59/61 typescript-eslint type-aware rules at 12–18x the speed of ESLint, and `--type-check` reports compiler errors from the same program, so one pass does lint and typecheck. Biome is about 15x faster than ESLint without plugins in its own benchmark, but has no type-aware rules there. With ESLint, the main levers are `--cache` (re-lints only changed files) and passing only the changed files.

### Cited Findings
- Install `oxlint` + `oxlint-tsgolint@7`; run `oxlint --type-aware`, add `--type-check` for TS diagnostics, `--debug timings` for per-rule cost. Config `options.typeAware` / `options.typeCheck` (root only). The version number encodes the TS version (v7.0.2000 = TS 7.0.2, patch 0). — [Oxc blog, 22 Jul 2026](https://oxc.rs/blog/2026-07-22-type-aware-linting-stable)
- Benchmarks (M4 Pro 12-core, tsgolint vs ESLint+typescript-eslint): vscode 83.2s→6.96s (12x), typescript 27.2→1.94s (14x), typeorm 13.2→0.75s (18x), vuejs/core 12.3→0.95s (13x). — [Oxc blog](https://oxc.rs/blog/2026-07-22-type-aware-linting-stable)
- Alpha (Dec 2025) had 43 rules, ~10x speed, and OOM problems on very large codebases. — [Oxc alpha post](https://oxc.rs/blog/2025-12-08-type-aware-alpha); [InfoQ](https://infoq.com/news/2026/09/tsgolint-oxlint-typescript). The README claims 20–40x vs ESLint. — [tsgolint repo](https://github.com/oxc-project/tsgolint) (vendor claims differ: 12–18x vs 20–40x)
- An independent benchmark found `oxlint --type-aware` noticeably slower than plain oxlint, which is expected. — [peterbe.com](https://www.peterbe.com/plog/benchmarking-oxlint-vs-biome)
- Biome's benchmark: ~15x faster than ESLint (no plugins), ~4x single-threaded, using only rules shared by both and no type-aware rules. A benchmark repo puts oxlint at about 2x Biome. — [Biome benchmark README mirror](https://github.com/chansuke/biome/blob/main/benchmark); [BenchJavaScriptLinter](https://github.com/CodeEditorLand/BenchJavaScriptLinter)
- ESLint `--cache` stores results in `.eslintcache` so only changed files are processed. Running without `--cache` deletes the cache file. `--cache-location` sets the path. `--cache-strategy content` (vs metadata/mtime) is used in practice and avoids invalidation after git checkout, though its documentation was not found in the results. `eslint_d` keeps a warm daemon. — [ESLint CLI (archived)](https://archive.eslint.org/docs/4.0.0/user-guide/command-line-interface); [eslint_d](https://github.com/dpinol/eslint_d.js)

### Inferences
- The project uses ESLint 10 with a suppressions baseline. Possible fast paths: (a) `eslint --cache --cache-strategy content <changed files>`, or (b) run oxlint first for the per-change loop and keep ESLint for the full gate. If the ESLint config uses type-aware rules, (c) `oxlint --type-aware --type-check` could replace both the per-change lint and `tsgo --noEmit` in one process, but only after checking rule parity with the current config.
- Type-aware rules (both ESLint and tsgolint) build the whole program, so "lint only changed files" saves less with type-aware rules than with syntactic-only ones.

### Gaps
- The official ESLint docs for `--cache-strategy` and ESLint 10's suppressions-plus-cache interaction were not fetched. No independent tsgolint-vs-ESLint benchmark was found.

## 5. What these techniques catch and miss; recommended per-change combination under ~10 s

### Takeaway
Use layers. Run a whole-program type check with native TS (fast enough to never scope), a lint pass on changed files (or oxlint on everything), and Vitest restricted to the changed-file graph. Upgrading to Vitest ≥5.0.4 with `recordDependencies` would catch runtime-only imports. Add always-run triggers for configs, setup files and data assets, and keep a full suite as the pre-commit/merge gate. Every selection system surveyed, from Meta and Launchable to Datadog and Nx, either accepts a small miss rate or has known blind spots, and all recommend periodic full runs.

### Cited Findings
- Static-graph selection misses dynamic imports and requires (Vitest, Jest docs). Recorded deps miss code not executed in the recorded run and partial-run records (PR #11515). Coverage-based selection misses dependency, compiler-option, external-service and data-file changes (Datadog). ML selection misses about 0.1% of faulty changes and ~5% of individual failures (Meta). — [Vitest CLI](https://vitest.dev/guide/cli); [Jest CLI](https://jestjs.io/docs/cli); [vitest #11515](https://github.com/vitest-dev/vitest/pull/11515); [Datadog TIA](https://docs.datadoghq.com/tests/test_impact_analysis/); [arXiv 1810.05286](https://export.arxiv.org/abs/1810.05286)
- Launchable recommends "an infrequent defensive full test run". — [Launchable](https://launchableinc.com/predictive-test-selection)
- TAP: failing tests sit "closer" to the code they test, which supports nearest-graph selection as a high-yield first pass. — [Memon et al.](https://www.cs.umd.edu/~atif/pubs/Memon_2017_TGC_3103112.3103143-abstract.html)

### Inferences (recommended concrete combo for this repo; estimates, not measurements)
1. `tsgo --noEmit -p tsconfig.json` on the whole program, optionally `--incremental` with a persisted tsbuildinfo. Expected ~1–3 s for ~200k LOC by the official ratios. After moving to TS 7.0.x stable: drop the native-preview pin, check `types` (new default `[]`), and confirm there is no `baseUrl`.
2. Lint changed files only, either `eslint --cache --cache-strategy content $(git diff --name-only --diff-filter=ACMR HEAD -- '*.ts')` or `oxlint` on the repo (sub-second for syntactic rules).
3. `vitest run --changed HEAD` (uncommitted changes) or `vitest related --run <files>`. Configure `forceRerunTriggers` so changes to `vitest.config.*`, setup files, `package.json` and shader/data assets rerun everything. On Vitest ≥5.0.4, add `--experimental.recordDependencies` so workers and computed imports that actually ran are tracked. Run once in full to seed the records.
4. Known blind spots to cover outside the per-change loop: Web Worker modules not reached by test imports, assets read via fs/fetch, shared global or GPU state between tests, and visual/rendering regressions (which no test selection replaces). Keep `npm test` (full ~3 min) as the gate before commit, as Meta, Launchable and Datadog all do.
5. Hub modules such as `src/core/*`, barrels and `main.ts` will fan out to most specs. For those changes the per-change loop gets close to a full run. Splitting barrels shrinks the related set.

### Gaps
- `forceRerunTriggers` was not documented on the fetched CLI page, so its exact defaults in Vitest 4.1/5 were not verified (it is a config option, not a CLI flag, in that page's view).
- No measured numbers for this repo. All seconds above are extrapolations from published ratios.
